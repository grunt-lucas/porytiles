# Project Structure Refactoring Plan

## Porytiles Utility Directory
Porytiles will create a `porytiles` directory in the `pokeemerald` project -- this directory will store configurations and artifact checksums.
```
pokeemerald/
├─ porytiles/
│  ├─ config.yaml <-- project-global config
│  ├─ config.local.yaml
│  ├─ tilesets/
│  │  ├─ gTileset_PorytilesTest/ <-- directory names use exact tileset name from 'src/data/tilesets/headers.h'
│  │  │  ├─ config.local.yaml
│  │  │  ├─ artifact_checksums.json
│  │  │  ├─ original_artifacts.json
│  │  ├─ gTileset_General/
│  │  │  ├─ config.yaml <-- tileset-specific config
│  │  │  ├─ artifact_checksums.json
│  │  │  ├─ original_artifacts.json
│  ├─ layouts/
```
`ProjectArtifactChecksumProvider::cache_tileset_checksums` will write here instead of the tileset root.
We'll want to change the key paths to relativize against the project root instead of the tileset root.

This change will also require us to remove the config handling from TilesetRepo.
It definitely doesn't belong there.

### `original_artifacts.json`
`original_artifacts.json` is generated by the first-time import.
We'll discuss this more later, but here is a quick rundown:

1. first-time import will overwrite the tileset values in `src/data/tilesets/headers.h`
2. `original_artifacts.json` will store the original values so they can possibly be restored later

`original_artifacts.json` presence in the tileset directory is the "source of truth" for if a tileset is Porytiles-managed.
Instead of doing brittle things like parsing the `.callback` field in `src/data/tilesets/headers.h`,
we can simply check if `original_artifacts.json` is present in the tileset utility directory.

```json
{
    ".tiles": "gTilesetTiles_General",
    ".palettes": "gTilesetPalettes_General",
    ".metatiles": "gMetatiles_General",
    ".metatileAttributes": "gMetatileAttributes_General",
    ".callback": "InitTilesetAnim_General"
}
```

This will also allow us to easily support a `restore-tileset` command,
which users can call if they don't like the changes Porytiles is making and want to reset things and start fresh.

For tilesets which started out life as Porytiles tilesets (created via `create-tileset`),
there will be no `original_artifacts.json` file so `restore-tileset` can give an error.

### Layouts
We'll support layouts later. They'll work similarly.

## First-Time Import IS NOT TilesetRepo::Load
The standard `TilesetRepo::load` assumes that discovered artifacts exist at their deterministic key locations.
For vanilla imports, frames are scattered wherever INCBIN declarations point—not at deterministic paths.

### The Core Insight
**Import is not a load operation.** It's a **migration/transformation**:

| Operation | Source Paths | Destination Paths |
|-----------|--------------|-------------------|
| **Import** | Scattered (parsed from INCBINs referenced in `src/data/tilesets/headers.h`) | Deterministic |
| **Load** | Deterministic | N/A (in-memory) |
| **Save** | N/A (in-memory) | Deterministic |

TilesetRepo handles Load/Save with deterministic paths. Import bridges from the chaotic vanilla world to the deterministic Porytiles world.

### The New Three-Workflow Model
```
┌─────────────────────────────────────────────────────────────────┐
│                         IMPORT (one-time)                       │
│  Vanilla tileset → VanillaTilesetImporter → TilesetRepo::save   │
│  (scattered paths)        (reads chaos)        (writes order)   │
└─────────────────────────────────────────────────────────────────┘
                                ↓
                    Tileset is now "Porytiles-managed"
                                ↓
┌─────────────────────────────────────────────────────────────────┐
│                    COMPILE (repeatable)                         │
│  TilesetRepo::load(porytiles) → transform → TilesetRepo::save   │
│  (deterministic)                           (deterministic)      │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                   DECOMPILE (repeatable)                        │
│  TilesetRepo::load(porymap) → transform → TilesetRepo::save     │
│  (deterministic)                         (deterministic)        │
└─────────────────────────────────────────────────────────────────┘
```
**NOTE:** compile and decompile are operating on the Porytiles-managed assets ONLY.
These operations never touch the original assets from which we imported.
This is a nice feature, it means Porytiles is truly surgical.
It won't clobber a user's original tileset artifacts,
making it trivial to restore if the user doesn't like what Porytiles did for a specific tileset.

### The Key Invariant
> **Once Import completes, the tileset is "Porytiles-managed" and all key generation is deterministic.**

This means:
- `anim.yaml` exists → Porytiles component can be discovered/loaded
- `generated_anim_code.h` exists → Porymap component can be discovered/loaded
- All frames are at deterministic paths → `key_for_*_anim_frame` works for both read and write

### Why NOT Put This in TilesetRepo?
If we added `load_vanilla_first_time` to TilesetRepo:
1. **Wrong abstraction level** — "vanilla" is a use-case concept, not a persistence concept
2. **Leaky abstraction** — TilesetRepo would need to know about INCBIN parsing, `tileset_anims.c`, etc.
3. **Breaks SRP** — TilesetRepo's job is artifact persistence with deterministic keys, not migration

This follows the **Repository Pattern** correctly: repositories provide a collection-like interface for domain objects. They shouldn't know about data migration or transformation between different storage formats. That's a **use case** concern, handled by an application service that orchestrates the migration.

## Import: Project State Before And After
In order to explain the import process clearly,
we'll show the pokeemerald project state before and after the import of `gTileset_General`.

### Key Porytiles Configuration Values
Porytiles will support four new configuration values:
```
tileset.paths.primary.src
tileset.paths.primary.bin
tileset.paths.secondary.src
tileset.paths.secondary.bin
```
Porytiles will consult these config values to decide where to place its managed assets.

It will place Porytiles-format assets at the path specified by `tileset.paths.primary.src`,
in a subdirectory `<tileset_name>/porytiles_src`.

It will place Porymap-format assets at the path specified by `tileset.paths.primary.bin`,
in a subdirectory `<tileset_name>/porytiles_bin`.

Defaults are:
```
tileset.paths.primary.src = data/tilesets/primary
tileset.paths.primary.bin = data/tilesets/primary
tileset.paths.secondary.src = data/tilesets/secondary
tileset.paths.secondary.bin = data/tilesets/secondary
```

With this project structure, `ProjectTilesetArtifactKeyProvider` key_for methods can be deterministic.
We just look in the `porytiles_src` directory under `tileset.paths.primary.src/<tileset_name>`
and `porytiles_bin` directory under `tileset.paths.primary.bin/<tileset_name>`
and the relative paths under these dirs are fixed and deterministic.
