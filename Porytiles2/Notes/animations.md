# Animations

## Summary
Detailed overview of animation handling.
Since decompilation-recompilation and patch compilation
are such a big piece of the Porytiles2 flow,
animation handling needs to be transparently symmetrical.

## Driver Code Sample
Here's a sample of all the driver code we need to be able to both parse and generate.
The animation definitions are located in `src/tileset_anims.c`.
Each animation has with it various associated frame arrays and queue functions.
```c++
// Need a definition for each frame file, can generate this automatically
const u16 gTilesetAnims_PorytilesAnimExample_Flower_Frame0[] = INCBIN_U16("data/tilesets/primary/porytiles_anim_example/anim/flower_red/00.4bpp");
const u16 gTilesetAnims_PorytilesAnimExample_Flower_Frame1[] = INCBIN_U16("data/tilesets/primary/porytiles_anim_example/anim/flower_red/01.4bpp");
const u16 gTilesetAnims_PorytilesAnimExample_Flower_Frame2[] = INCBIN_U16("data/tilesets/primary/porytiles_anim_example/anim/flower_red/02.4bpp");

// Frames need to be arranged into an array, the user will have to configure this with "frames" array
const u16 *const gTilesetAnims_PorytilesAnimExample_Flower[] = {
    gTilesetAnims_PorytilesAnimExample_Flower_Frame0,
    gTilesetAnims_PorytilesAnimExample_Flower_Frame1,
    gTilesetAnims_PorytilesAnimExample_Flower_Frame0,
    gTilesetAnims_PorytilesAnimExample_Flower_Frame2
};

static void QueueAnimTiles_PorytilesAnimExample_Flower(u16 timer)
{
    u16 i = timer % ARRAY_COUNT(gTilesetAnims_PorytilesAnimExample_Flower);
    // 4 * TILE_SIZE_4BPP - this can be generated by looking at the frame count, the '4' here just means there are four frames
    // TILE_OFFSET_4BPP(1) - this offset should be generated by Porytiles,
    // each animation has a unique offset in tiles.png that we can control
    // Can we optionally allow users to specify their own offsets?
    // Regardless, we'll need to add some custom code to TilesPngWorkspace
    // so that the compilation job can pre-insert the anim tiles at the right offset
    AppendTilesetAnimToBuffer(gTilesetAnims_PorytilesAnimExample_Flower[i], (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(1)), 4 * TILE_SIZE_4BPP);
}

// Some tilesets look like this:
static void QueueAnimTiles_EverGrande_Flowers(u16 timer_div, u8 timer_mod)
{
    timer_div -= timer_mod;
    timer_div %= ARRAY_COUNT(gTilesetAnims_EverGrande_Flowers);

    AppendTilesetAnimToBuffer(gTilesetAnims_EverGrande_Flowers[timer_div], gTilesetAnims_EverGrande_VDests[timer_mod], 4 * TILE_SIZE_4BPP);
}

// VDests looks like:
u16 *const gTilesetAnims_EverGrande_VDests[] = {
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 224)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 228)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 232)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 236)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 240)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 244)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 248)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 252))
};

// TODO: figure out the details of this VDests thing
// See Evergrande City flowers, but basically, it allows the programmer to have a bunch of identical
// flowers running on different animation offsets, so instead of moving in perfect sync, they have a "wave"
// quality wherein each flower is moving at a different phase.

static void TilesetAnim_PorytilesAnimExample(u16 timer)
{
    // This is how we handle tilesets with multiple animations
    // There are two ways to do this, each is detaile below.

    // The timer modulo factor here should be user-configurable
    // 16 and 8 are the most common values
    // The factor is effectively saying: every 16 frames, update this animation
    // See: https://github.com/grunt-lucas/porytiles/wiki/Adding-Animations#main-animation-driver

    // This style offsets each animation update by a frame. With this approach,
    // you won't have the strange visual experience of every animated object updating
    // at the exact same time.
    if (timer % 16 == 0)
        QueueAnimTiles_PorytilesAnimExample_Flower(timer / 16);
    if (timer % 16 == 1)
        QueueAnimTiles_General_Water(timer / 16);
    if (timer % 16 == 2)
        QueueAnimTiles_General_SandWaterEdge(timer / 16);
    if (timer % 16 == 3)
        QueueAnimTiles_General_Waterfall(timer / 16);
    if (timer % 16 == 4)
        QueueAnimTiles_General_LandWaterEdge(timer / 16);
    
    // Alternatively, we can probably just generate this, which is simpler.
    if (timer % 16 == 0) {
        QueueAnimTiles_PorytilesAnimExample_Flower(timer / 16);
        QueueAnimTiles_General_Water(timer / 16);
        QueueAnimTiles_General_SandWaterEdge(timer / 16);
        // etc.
    }
    
    // Users can specify a "frame_offset" value for each animation to specify where in this
    // IF structure they want each animation to be placed
}

// Init function values will need to be configured
// However, these defaults should work for most tilesets
void InitTilesetAnim_PorytilesAnimExample(void)
{
    sPrimaryTilesetAnimCounter = 0;
    // For secondary tilesets, just do:
    // sSecondaryTilesetAnimCounterMax = sPrimaryTilesetAnimCallback
    sPrimaryTilesetAnimCounterMax = 256;
    sPrimaryTilesetAnimCallback = TilesetAnim_PorytilesAnimExample;
}
```

## Configuration
Users can specify their animation parameters in the Porytiles component of a tileset,
i.e. in a file `porytiles/anim.yaml`
Here's an example `anim.yaml` file.
```yaml
# the animation name
flower:
  # users can specify this if they want
  sPrimaryTilesetAnimCounter: 0
  # this is modulus used in the main TilesetAnim function
  frame_factor: 16
  # this is the value on the right of the equals sign in the "i % 16 == 1" constructs
  frame_offset: 1
  # this array defines the order of the frames, e.g. the "const u16 *const gTilesetAnims_PorytilesAnimExample_Flower[]"
  frames: [0, 1, 0, 2]
```

## Key Frames
We'll retain the "key frame" concept.
However, it will be significantly more intuitive.
Users will still have to provide a "key.png" in the Porytiles component,
but they should be able to just use a copy of 0.png as the key frame without hitting
https://github.com/grunt-lucas/porytiles/issues/60
Our compilation algo is significantly upgraded and can easily accommodate this now without causing a recurrence of this issue.

Compilation algorithm, when in the assign step, can easily detect if it's trying to assign a key frame tile.
It can then branch into different logic, wherein it figures out which pal will accommodate the full animation, to compute the pal index.
It will also be able to check where in `TilesPngWorkspace` this anim starts, so it can compute the tile index and offset.
Finally, it can compare the orientation of the tile it encountered with the original 0.png to compute flip bits.

## Tileset Modelling
How should we model animations in the Tileset aggregate type?
We already have frame PNGs defined for both the Porytiles and Porymap components.
In addition to frame PNGs, we'll need an `AnimationParams` class
which stores the animation data defined in `anim.yaml` (for the Porytiles component)
and implicitly in the C code (for the Porymap component).

It will be the responsibility of the artifact reader/writer classes to figure out how to
read the `anim.yaml` file into an `AnimationParams`
as well as how to parse the C code into an `AnimationParams`.

Final note: the Porytiles/Porymap components will actually store a `std::map<std::string, AnimationParams>`
so that each anim's params can be identified via the animation name.

### Reading And Writing

The `ProjectTilesetArtifactReader` will need to be able to:
- read `anim.yaml` contents into the PorytilesTilesetComponent's `std::map<std::string, AnimationParams>`
- (on first-ever import, more on this below)
  - read `src/data/tilesets/headers.h` and `src/tileset_anims.c` into PorymapTilesetComponent's `std::map<std::string, AnimationParams>`
- (on subsequent imports/compiles, more on this below)
  - from tileset's data folder read generated C in the `include/generated_anim_code.h` into PorymapTilesetComponent's `std::map<std::string, AnimationParams>`
  - we'll know to read from `include/generated_anim_code.h` iff it exists, otherwise we read from the default game files

The `ProjectTilesetArtifactWriter` will need to be able to:
- write an `anim.yaml` based on contents of PorytilesTilesetComponent's `std::map<std::string, AnimationParams>`
  - unfortunately this means we'll clobber user's yaml comments every time, no way around that I don't think
  - given this, would it be more natural to make it a JSON file, since JSON doesn't support comments?
- (on first-ever import, more on this below)
  - write generated code to `include/generated_anim_code.h`
  - User must manually (more on this below):
    - edit `src/data/tilesets/headers.h` so that the callback for `gTileset_PorytilesAnimExample` is set to our "hijacked" Porytiles managed anim code
    - add a declaration for our Porytiles-managed init function to `include/tileset_anims.h`
    - add `#include "data/tilesets/primary/porytiles_anim_example/include/generated_anim_code.h"` to the bottom of `src/tileset_anims.c`
- (on subsequent imports/compiles, more on this below)
  - simply update `data/tilesets/primary/porytiles_anim_example/include/generated_anim_code.h`
  - the main game engine's anim C harness code is already pointing at our managed header, thanks to one-time user manual edits

## Import Handling

### First Time Import
When importing a tileset for the very first time, i.e. it doesn't have a `porytiles` folder yet:
- Initial tileset load
  - No Porytiles component to load
  - Read Porymap component AnimParams map -> comes from the default anim files
  - Load other artifacts
- Run decompilation logic
  - Perform regular metatile / attribute decomp steps
  - Decomp anim frames
  - Use AnimationParams to figure out where on the three layer PNGs we should place the 0.png artwork
    - some vanilla tilesets just put random crap in tiles.png that doesn't correspond to 0.png
    - which means if we just decompile straight, it won't recompile correctly
    - we need to use the AnimParams to figure out which metatile locations should have 0.png frame tiles
  - copy the Porymap `std::map<std::string, AnimationParams>` to the Porytiles side
- Save tileset
  - write `include/generated_anim_code.h"` for the first time 
  - write `porytiles/anim.yaml` for the first time
  - save anim frames
  - save other artifacts

### Subsequent Imports
On subsequent imports, `porytiles/anim.yaml` exists as does `include/generated_anim_code.h`.
- Initial tileset load
  - Read Porymap component AnimParams map -> this time from `include/generated_anim_code.h`
  - Read Porytiles component AnimParams map -> this one from `porytiles/anim.yaml`
  - Load other artifacts
- Run decomp logic
  - steps exactly same as above
- Save tileset
  - overwrite `include/generated_anim_code.h"` contents
  - overwrite `porytiles/anim.yaml` contents
  - save anim frames
  - save other artifacts

## Compile Handling
This one is similar to import, but it doesn't have two cases. Just one case:

### Flow
- Initial tileset load
  - Read Porymap component AnimParams map -> this time from `include/generated_anim_code.h`
  - Read Porytiles component AnimParams map -> this one from `porytiles/anim.yaml`
  - Load other artifacts
- Run compilation logic
  - Create "aggregate" logical tiles from the corresponding tile across all frames of an anim, just like how Porytiles1 does things
  - Use params from `include/generated_anim_code.h"` to figure out where in `TilesPngWorkspace` we need to reserve space for anim tiles
  - Later in the assignment step, when encountering a tile that matches 0.png, link to animation location instead of inserting into `TilesPngWorkspace` normally
- Save tileset
  - overwrite `include/generated_anim_code.h"` contents
  - overwrite `porytiles/anim.yaml` contents
  - save anim frames
  - save other artifacts

## User Responsibilities
Users will be responsible for manually editing a couple files in order to "onboard" their tileset's animation handling into Porytiles.
This will make the whole process more explicit and less error prone.
Also, it will save us from having to modify files that Porymap also manages, reducing potential for clobbering / corruption.

### `src/data/tilesets/headers.h`
Each tileset has a definition struct defined in `src/data/tilesets/headers.h`.
Porymap manages this file, so we don't want to touch it.
The struct for theoretical tileset `PorytilesAnimExample` will look like:
```c++
const struct Tileset gTileset_PorytilesAnimExample =
{
    .isCompressed = TRUE,
    .isSecondary = FALSE,
    .tiles = gTilesetTiles_PorytilesAnimExample,
    .palettes = gTilesetPalettes_PorytilesAnimExample,
    .metatiles = gMetatiles_PorytilesAnimExample,
    .metatileAttributes = gMetatileAttributes_PorytilesAnimExample,
    // User will need to modify the .callback field to refer to Porytiles generated Init function, it will be NULL by default
    // Note the PorytilesManaged moniker
    // Porytiles inserts this to prevent name collisions when importing tilesets that already have defined animation code
    .callback = InitTilesetAnim_PorytilesManaged_PorytilesAnimExample,
};
```

### `include/tileset_anims.h`
Every tileset declares its anim init function in `include/tileset_anims.h`. They look like this:
```c++
void InitTilesetAnim_General(void);
// Other inits...

// User must declare the Porytiles anim init function here
// It will be defined for them already in:
//   data/tilesets/primary/porytiles_anim_example/include/generated_anim_code.h
void InitTilesetAnim_PorytilesManaged_PorytilesAnimExample(void);

#endif // GUARD_TILESET_ANIMS_H
```

### `src/tileset_anims.c`
User will have to add an include statement at the bottom of this file
so that Porytiles generated code gets included and compiled.

`src/tileset_anims.c` sample:
```c++
// Other stuff...
static void BlendAnimPalette_BattleDome_FloorLightsNoBlend(u16 timer)
{
    CpuCopy16(sTilesetAnims_BattleDomeFloorLightPals[timer % ARRAY_COUNT(sTilesetAnims_BattleDomeFloorLightPals)], &gPlttBufferUnfaded[BG_PLTT_ID(8)], PLTT_SIZE_4BPP);
    if ((u8)FindTaskIdByFunc(Task_BattleTransition_Intro) == TASK_NONE)
    {
        BlendPalette(BG_PLTT_ID(8), 16, gPaletteFade.y, gPaletteFade.blendColor & 0x7FFF);
        if (!--sSecondaryTilesetAnimCounterMax)
            sSecondaryTilesetAnimCallback = NULL;
    }
}

// Porytiles manual user includes:
#include "data/tilesets/primary/porytiles_anim_example/include/generated_anim_code.h"
``` 

## Special Case - Vanilla Tilesets With Duplicate Key Frames
Some vanilla animations, notable Primary General `water`, contain key-frame duplication.
That is, `tiles.png` contains two completely identical tiles in two different spots within an animated region,
and the rest of the frame subtiles corresponding to those key frame tiles are distinct.

This means we have a fundamental ambiguity if we simply imported/recompiled according to the above procedure.
Luckily, we can detect this ambiguity during the import step and mitigate.
Here is the plan:

The `AnimationDecompiler` should track all key frame tiles globally.
If it EVER hits a duplicate, we have to enter special handling mode,
wherein we add custom override blocks to `anim.yaml`. They can look like this:

```yaml
water:
  sPrimaryTilesetAnimCounter: 0
  frame_factor: 16
  frame_offset: 1
  frames: [0, 1, 0, 2]
  overrides:
    - metatile:
        id: 22
        layer: bottom
        subtile: northwest
        key_frame_subtile: 2
```
