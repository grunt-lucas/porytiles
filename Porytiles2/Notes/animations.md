# Animations

## Summary
Detailed overview of animation handling.
Since decompilation-recompilation and incremental compilation
are such a big piece of the Porytiles2 flow,
animation handling needs to be transparently symmetrical.

```c++
// Need a definition for each frame file, can generate this automatically
const u16 gTilesetAnims_PorytilesPrimaryTutorial_Flower_Frame0[] = INCBIN_U16("data/tilesets/primary/porytiles_primary_tutorial/anim/flower_red/00.4bpp");
const u16 gTilesetAnims_PorytilesPrimaryTutorial_Flower_Frame1[] = INCBIN_U16("data/tilesets/primary/porytiles_primary_tutorial/anim/flower_red/01.4bpp");
const u16 gTilesetAnims_PorytilesPrimaryTutorial_Flower_Frame2[] = INCBIN_U16("data/tilesets/primary/porytiles_primary_tutorial/anim/flower_red/02.4bpp");

// Frames need to be arranged into an array, the user will have to configure this with "frames" array
const u16 *const gTilesetAnims_PorytilesPrimaryTutorial_Flower[] = {
    gTilesetAnims_PorytilesPrimaryTutorial_Flower_Frame0,
    gTilesetAnims_PorytilesPrimaryTutorial_Flower_Frame1,
    gTilesetAnims_PorytilesPrimaryTutorial_Flower_Frame0,
    gTilesetAnims_PorytilesPrimaryTutorial_Flower_Frame2
};

static void QueueAnimTiles_PorytilesPrimaryTutorial_Flower(u16 timer)
{
    u16 i = timer % ARRAY_COUNT(gTilesetAnims_PorytilesPrimaryTutorial_Flower);
    // 4 * TILE_SIZE_4BPP - this can be generated by looking at the frame count, the '4' here just means there are four frames
    // TILE_OFFSET_4BPP(1) - this offset should be generated by Porytiles, each animation has a unique offset in tiles.png that we can control
    // Can we optionally allow users to specify their own offsets?
    AppendTilesetAnimToBuffer(gTilesetAnims_PorytilesPrimaryTutorial_Flower[i], (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(1)), 4 * TILE_SIZE_4BPP);
}

// Some tilesets look like this:
static void QueueAnimTiles_EverGrande_Flowers(u16 timer_div, u8 timer_mod)
{
    timer_div -= timer_mod;
    timer_div %= ARRAY_COUNT(gTilesetAnims_EverGrande_Flowers);

    AppendTilesetAnimToBuffer(gTilesetAnims_EverGrande_Flowers[timer_div], gTilesetAnims_EverGrande_VDests[timer_mod], 4 * TILE_SIZE_4BPP);
}

// VDests looks like:
u16 *const gTilesetAnims_EverGrande_VDests[] = {

    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 228)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 232)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 236)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 240)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 244)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 248)),
    (u16 *)(BG_VRAM + TILE_OFFSET_4BPP(NUM_TILES_IN_PRIMARY + 252))
};

// TODO: figure out the details of this VDests thing
// See Evergrande City flowers, but basically, it allows the programmer to have a bunch of identical
// flowers running on different animation offsets, so instead of moving in perfect sync, they have a "wave"
// quality wherein each flower is moving at a different phase.

static void TilesetAnim_PorytilesPrimaryTutorial(u16 timer)
{
    // This is how we handle tilesets with multiple animations
    // There are two ways to do this, each is detaile below.

    // The timer modulo factor here should be user-configurable
    // 16 and 8 are the most common values
    // The factor is effectively saying: every 16 frames, update this animation
    // See: https://github.com/grunt-lucas/porytiles/wiki/Adding-Animations#main-animation-driver

    // This style offsets each animation update by a frame. With this approach,
    // you won't have the strange visual experience of every animated object updating
    // at the exact same time.
    if (timer % 16 == 0)
        QueueAnimTiles_PorytilesPrimaryTutorial_Flower(timer / 16);
    if (timer % 16 == 1)
        QueueAnimTiles_General_Water(timer / 16);
    if (timer % 16 == 2)
        QueueAnimTiles_General_SandWaterEdge(timer / 16);
    if (timer % 16 == 3)
        QueueAnimTiles_General_Waterfall(timer / 16);
    if (timer % 16 == 4)
        QueueAnimTiles_General_LandWaterEdge(timer / 16);
    
    // Alternatively, we can probably just generate this, which is simpler.
    if (timer % 16 == 0) {
        QueueAnimTiles_PorytilesPrimaryTutorial_Flower(timer / 16);
        QueueAnimTiles_General_Water(timer / 16);
        QueueAnimTiles_General_SandWaterEdge(timer / 16);
        // etc.
    }
    
    // Users can specify a "frame_offset" value for each animation to specify where in this
    // IF structure they want each animation to be placed
}

// Init function values will need to be configured
// However, these defaults should work for most tilesets
void InitTilesetAnim_PorytilesPrimaryTutorial(void)
{
    sPrimaryTilesetAnimCounter = 0;
    // For secondary tilesets, just do:
    // sSecondaryTilesetAnimCounterMax = sPrimaryTilesetAnimCallback
    sPrimaryTilesetAnimCounterMax = 256;
    sPrimaryTilesetAnimCallback = TilesetAnim_PorytilesPrimaryTutorial;
}
```

## Configuration
Here's an example of an animation parameters file:
```json
{
  "flower": {
    "sPrimaryTilesetAnimCounter": 0, // users can specify this if they want
    "frame_factor": 16, // this is modulus used in the main TilesetAnim function
    "frame_offset": 1,  // this is the value on the right of the equals sign in the "i % 16 == 1" constructs
    "frames": [ // this array defines the order of the frames, e.g. the "const u16 *const gTilesetAnims_PorytilesPrimaryTutorial_Flower[]"
      0,
      1,
      0,
      2
    ],
    // metatile definitions here
    "metatiles": [
      {
        "id": 22,
        "layer": "middle",
        "subtile": "northwest",
        "frame_subtile_index": 1,
        "hflip": true,
        "vflip": false
      }
    ]
  }
}
```
We can spit out a warning if the user specified a metatile subtile
that didn't match a subtile in 00.png of the corresponding animation.
E.g. in the example above,
if on the middle layer sheet the northwest subtile of metatile 22 is not the hflipped version of `flower`'s 00.png subtile 1,
then we warn the user that the contents of the layer sheet doesn't match the configured animation,
and the compilation result may not look as they expect.


### No More Key Frames!
Instead of clunky key frames,
we can require the user to supply animation information in the animation config file.
Since we're already requiring users to supply a config file to specify various anim params,
we can make users specify the actual animated metatiles there as well.

Is this method a bit more tedious, especially for complex animations like water?
Yeah probably. But it's so much less error-prone and ambiguous than trying to do key frame management.
Plus, JSON is a format users are used to. Better to make them do some tedious JSON munging to get everything working,
as opposed to having to explain the key-frame-missing-colors warning for the 10,000th time
(which is understandable, because tbf that warning is super cryptic and basically just a bandaid for my shite design).

For convenience, we could generate some kind of command like:
`porytiles2 generate-anim-config petalburg`
wherein we look at the layer sheets for the given tileset,
try to match metatile subtiles to anim frames,
and if they match with specific flips then emit the JSON above.

### Import Handling
How to generate this when running an import?
We can infer the values in the params file by inspecting the animation code,
which contains hardcoded tileset offsets for each animation.
After everything is imported the first time,
on subsequent imports we can compute animation offsets via our generated anim code.

## Tileset Modelling
How should we model animations in the Tileset aggregate type?

### Porytiles Component
- Frame PNGs
- Container to store data from `animation_parameters.json`
  - See above for the format of the JSON
  - Could be something like `std::map<std::string, AnimationParams>`

### Porymap Component
- Compiled frame PNGs
- Animation driver code minimal representation
  - a specialized TilesetArtifactWriter can generate the actual full C code on save
  - Generated C code for `tileset_anims.c` should be in an include-able file like `generated_anim_code.h` or something similar 
  - Otherwise, the Tileset aggregate would have to store an awkward jumble of C code as a vector<string> or something else equally unwieldy

### Process
- We'll need a way to add `#include "data/tilesets/primary/porytiles_tutorial/generated_anim_code.h` if it's not present for relevant tileset
- We'll need a way to remove a vanilla tileset's animation code from `tileset_anims.c` when the tileset is imported for the first time
